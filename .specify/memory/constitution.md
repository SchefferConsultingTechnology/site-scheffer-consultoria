# scheffer-consultoria Constitution

# Constituição do scheffer-consultoria

## Core Principles

## Princípios Fundamentais

### I. Component-Driven UI (shadcn/ui First)

**EN —** New UI MUST reuse or extend the existing shadcn/ui primitives in `src/components/ui`
before a new UI dependency is introduced. New primitives MUST follow the established conventions:
Radix UI underneath, styling via Tailwind CSS utility classes, variants expressed with
`class-variance-authority`. Ad hoc styling or component libraries that duplicate existing
primitives are not permitted without justification.
Rationale: this is a marketing/institutional site where visual consistency is a core requirement;
a single design system keeps the site coherent and avoids uncontrolled dependency growth.

**PT-BR —** Novas interfaces DEVEM reutilizar ou estender os primitivos shadcn/ui já existentes em
`src/components/ui` antes que uma nova dependência de UI seja introduzida. Novos primitivos DEVEM
seguir as convenções estabelecidas: Radix UI por baixo, estilização via classes utilitárias do
Tailwind CSS, variantes expressas com `class-variance-authority`. Estilização improvisada ou
bibliotecas de componentes que dupliquem primitivos já existentes não são permitidas sem
justificativa.
Motivo: este é um site institucional/de marketing onde a consistência visual é um requisito
central; um único design system mantém o site coerente e evita crescimento descontrolado de
dependências.

### II. Type Safety & Quality Gates (NON-NEGOTIABLE)

**EN —** All code MUST type-check under the project's TypeScript configuration with no errors.
`npm run lint` (ESLint) and `npm run format` (Prettier) MUST be clean before a change is committed.
Generated files — `src/routeTree.gen.ts` and any other TanStack Router build artifact — MUST NOT
be hand-edited; they are regenerated by the router plugin from the routes in `src/routes`.
Rationale: there is no CI configured yet, so local lint/format/type-check are the only quality
backstop; hand-editing generated files causes silent drift and build breakage.

**PT-BR —** Todo o código DEVE passar na checagem de tipos da configuração TypeScript do projeto
sem erros. `npm run lint` (ESLint) e `npm run format` (Prettier) DEVEM estar limpos antes de uma
alteração ser commitada. Arquivos gerados — `src/routeTree.gen.ts` e qualquer outro artefato de
build do TanStack Router — NÃO DEVEM ser editados manualmente; eles são regenerados pelo plugin do
router a partir das rotas em `src/routes`.
Motivo: ainda não há CI configurado, então lint/format/checagem de tipos locais são a única
proteção de qualidade; editar arquivos gerados manualmente causa divergência silenciosa e quebra de
build.

### III. File-Based Routing Discipline

**EN —** Routes live under `src/routes` and follow TanStack Router's file-based routing
conventions. `src/router.tsx` and `src/routeTree.gen.ts` are derived artifacts of that convention
and MUST stay in sync via the standard dev/build tooling rather than manual edits.
Rationale: prevents divergence between the route file tree and the generated route table, which is
a common source of hard-to-diagnose navigation bugs.

**PT-BR —** As rotas ficam em `src/routes` e seguem as convenções de roteamento baseado em
arquivos do TanStack Router. `src/router.tsx` e `src/routeTree.gen.ts` são artefatos derivados
dessa convenção e DEVEM permanecer sincronizados via as ferramentas padrão de dev/build, nunca por
edição manual.
Motivo: evita divergência entre a árvore de arquivos de rotas e a tabela de rotas gerada, uma fonte
comum de bugs de navegação difíceis de diagnosticar.

### IV. Lovable Sync Integrity

**EN —** The branch connected to Lovable MUST remain in a working, buildable state at all times.
Published history on that branch MUST NOT be rewritten: no force-push, rebase, amend, or squash of
commits that have already been pushed.
Rationale: Lovable mirrors pushed commits into its own editor; rewriting history breaks that sync
and can cause the user to lose project history on Lovable's side (see `AGENTS.md`).

**PT-BR —** A branch conectada ao Lovable DEVE permanecer em estado funcional e buildável em todos
os momentos. O histórico já publicado nessa branch NÃO DEVE ser reescrito: nada de force-push,
rebase, amend ou squash de commits já enviados.
Motivo: o Lovable espelha os commits enviados em seu próprio editor; reescrever o histórico quebra
essa sincronização e pode fazer o usuário perder o histórico do projeto no lado do Lovable (veja
`AGENTS.md`).

### V. Simplicity & Content-First Delivery

**EN —** As a marketing/institutional site, prefer static content and server-rendered pages over
client-side complexity. New client state, dependencies, or abstractions MUST be justified by an
actual content or interaction need — not introduced speculatively.
Rationale: for a site whose primary goals are performance, SEO, and maintainability by a small
team, unnecessary architectural flexibility is a cost, not a benefit (YAGNI).

**PT-BR —** Por ser um site institucional/de marketing, deve-se preferir conteúdo estático e
páginas renderizadas no servidor em vez de complexidade no lado do cliente. Novo estado de cliente,
dependências ou abstrações DEVEM ser justificados por uma necessidade real de conteúdo ou interação
— nunca introduzidos de forma especulativa.
Motivo: para um site cujos objetivos principais são performance, SEO e manutenibilidade por uma
equipe pequena, flexibilidade arquitetural desnecessária é um custo, não um benefício (YAGNI).

## Technology Stack

## Stack Tecnológica

**EN —** React 19 on TanStack Start (SSR) with TanStack Router (file-based routing) and Vite 8 as
the build tool. Styling via Tailwind CSS v4 and the shadcn/ui component set (Radix UI primitives +
`class-variance-authority`). TypeScript is used throughout. Deployment builds target Cloudflare via
Nitro, orchestrated through `@lovable.dev/vite-tanstack-config` — its bundled plugins (TanStack
devtools, `tanstackStart`, `viteReact`, `tailwindcss`, `tsConfigPaths`, `nitro`, env injection, path
aliasing, React/TanStack dedupe) MUST NOT be duplicated in `vite.config.ts`. ESLint and Prettier are
the enforced linting/formatting stack. Both `bun.lock` and `package-lock.json` are currently
tracked; a change of package manager or removal of either lockfile is a deliberate decision, not an
incidental one.
Changing any element of this stack (framework, styling system, deployment target, package manager)
is a governance-level decision and MUST be reflected in an amendment to this constitution.

**PT-BR —** React 19 sobre TanStack Start (SSR) com TanStack Router (roteamento baseado em
arquivos) e Vite 8 como ferramenta de build. Estilização via Tailwind CSS v4 e o conjunto de
componentes shadcn/ui (primitivos Radix UI + `class-variance-authority`). TypeScript é usado em
todo o projeto. Os builds de deploy têm o Cloudflare como alvo via Nitro, orquestrados através do
`@lovable.dev/vite-tanstack-config` — seus plugins embutidos (TanStack devtools, `tanstackStart`,
`viteReact`, `tailwindcss`, `tsConfigPaths`, `nitro`, injeção de env, alias de path, dedupe de
React/TanStack) NÃO DEVEM ser duplicados em `vite.config.ts`. ESLint e Prettier são a stack de
lint/formatação obrigatória. Tanto `bun.lock` quanto `package-lock.json` estão versionados
atualmente; trocar o gerenciador de pacotes ou remover um dos lockfiles é uma decisão deliberada,
não incidental.
Alterar qualquer elemento dessa stack (framework, sistema de estilização, alvo de deploy,
gerenciador de pacotes) é uma decisão em nível de governança e DEVE ser refletida em uma emenda a
esta constituição.

## Development Workflow

## Fluxo de Desenvolvimento

**EN —** Before committing: run `npm run lint` and `npm run format`, and ensure the project still
type-checks. Before pushing to the Lovable-connected branch: run `npm run build` and confirm it
succeeds (Principle IV). Commits should be scoped to a single logical change and use a descriptive
message; already-pushed commits MUST NOT be amended, rebased, or force-pushed. No automated CI is
configured yet, so these checks are the contributor's responsibility until CI is introduced — at
which point this section MUST be amended to reflect it.

**PT-BR —** Antes de commitar: rode `npm run lint` e `npm run format`, e garanta que o projeto
ainda passa na checagem de tipos. Antes de enviar (push) para a branch conectada ao Lovable: rode
`npm run build` e confirme que ele é bem-sucedido (Princípio IV). Commits devem ser escopados a uma
única mudança lógica e usar mensagem descritiva; commits já enviados NÃO DEVEM ser amendados,
rebasados ou enviados com force-push. Ainda não há CI automatizado configurado, então essas
verificações são responsabilidade de quem contribui até que o CI seja introduzido — quando isso
acontecer, esta seção DEVE ser emendada para refletir isso.

## Governance

## Governança

**EN —** This constitution supersedes ad hoc conventions for this repository. Amendments are made
via the `/speckit-constitution` command, which MUST record version bumps per semantic versioning
(MAJOR for backward-incompatible principle removals/redefinitions, MINOR for new or materially
expanded principles/sections, PATCH for clarifications and wording) and MUST prepend a Sync Impact
Report describing the change. Feature work produced via `/speckit-plan` and `/speckit-implement`
MUST remain consistent with these principles; any necessary deviation MUST be explicitly justified
in the plan's Complexity Tracking section rather than silently introduced. `AGENTS.md` carries
additional Lovable-specific agent guidance alongside this constitution. Every section of this
constitution MUST be maintained in both English and Portuguese (pt-BR); an amendment that updates
one language version MUST update the other in the same change.

**PT-BR —** Esta constituição substitui convenções informais neste repositório. Emendas são feitas
via o comando `/speckit-constitution`, que DEVE registrar mudanças de versão segundo versionamento
semântico (MAJOR para remoção/redefinição de princípios incompatível com versões anteriores, MINOR
para princípios/seções novos ou materialmente ampliados, PATCH para esclarecimentos e ajustes de
texto) e DEVE anexar um Sync Impact Report no início do arquivo descrevendo a mudança. O trabalho
de features produzido via `/speckit-plan` e `/speckit-implement` DEVE permanecer consistente com
esses princípios; qualquer desvio necessário DEVE ser explicitamente justificado na seção de
Complexity Tracking do plano, em vez de introduzido silenciosamente. O `AGENTS.md` carrega
orientações adicionais específicas do Lovable para agentes, junto com esta constituição. Toda seção
desta constituição DEVE ser mantida em inglês e em português (pt-BR); uma emenda que atualize uma
versão de idioma DEVE atualizar a outra na mesma mudança.
